---
description: Plan, implement with a task agent, review with a reviewer agent, then hand off for my approval
argument-hint: "<goal and technical requirements, or a path to an approved plan file>"
---

Goal and requirements: $ARGUMENTS

Run this workflow in order.

1. Understand. Run `git status` and `git branch --show-current`, and note whether the current branch is the repo's default branch (compare with `git symbolic-ref --short refs/remotes/origin/HEAD`). Read the relevant code. If the request is unclear on a choice that changes the result, ask me before going further.
2. Plan. If the request names an existing plan file, read it and treat it as the approved plan, then go to step 3. Otherwise write a plan another agent could follow with no design decisions left open: context, ordered steps with exact files and symbols, the exact verification commands, and assumptions I can override. If the plan has several commits, group them into PRs, and for each commit state the exact files and the exact moments I must run commands (branch creation, local and production migrations, pushes). Save it to a local:// file, then print the full plan as chat text in the same turn (tool output is collapsed in my UI, so a path or a summary is not enough). End the turn with an ask whose question is one line offering Approve, Revise, or Cancel. Spawn nothing until I approve. On Revise, update the plan file, reprint the full updated plan as chat text, and ask again.
3. Implement. Spawn one `task` agent per commit, one commit at a time, so the working tree never holds two commits' work. Its brief must be complete on its own: the goal, exact files and symbols, acceptance criteria, the exact verification commands, and the CLAUDE.md rules that apply. Tell it that read-only git (status, diff, log, branch --show-current) is allowed, and that it must never run git add, git commit, git push, git stash, git checkout, git restore, git reset, or database commands. Tell it not to paste full diffs in its report, since I read the diff myself. For commits after the first, also give it the plan path and tell it to read `git log` to see what earlier commits already did. Do not print a full code preview before the implementer runs. Only when a commit has a real design alternative, show a short design note first (signatures and conditions, not full code) and ask me to choose. After each commit, run step 4, hand that commit off (step 8, commit part), and wait for me to commit it before starting the next.
   - Handoff file: tell the implementer to update the plan's handoff file (`<plan name>-handoff.md` next to the plan, if one exists) as part of the commit work. It sets the status, repo state, what is done and the next step to reflect this commit, and marks resolved open items as resolved. This file is outside the repo, so it is allowed and never part of the diff.
   - Spawn summary: in the same turn, as the last chat text right above each implementer `task` call, print a short plain language summary of the commit so the permission prompt has context. Use this order and keep it scannable: the commit's position ("PR 5, commit 2 of 4"), what the commit is for in one or two sentences, the files it changes with one line each on what changes, the tests it adds and what they protect, what is deliberately left out, and any decisions already settled with me. Words only, no code and no diff, so it does not conflict with the no code preview rule above. Do not skip it for later commits or for a resumed session.
4. Verify. After every commit, run the verification commands yourself and record the real results. If all pass, hand the commit off. If any fail, send the output to the implementer to fix, up to 2 fix attempts, then stop and report.
5. Review. Review once per PR, not per commit. For a one-commit job, review the uncommitted diff, including any new untracked files, before the hand-off. For a multi-commit PR, review after I have committed the last commit of that PR, using the full branch diff against the default branch (`git diff <default>...HEAD`) plus any untracked files, and the original requirements for the whole PR. Spawn one `reviewer` agent. It must not edit files, and read-only git is allowed. Write its brief as an adversarial review, not a general one:
   - Persona: "You are a hostile reviewer. Assume the change is wrong until you have disproved it from the code. Your job is to find defects the author and the tests missed. No praise, and no style opinions outside the listed rules."
   - Output: each finding has `file:line`, a concrete failure scenario (the input or state that triggers it), and a label of blocking or non-blocking. If it reports no findings, it MUST first list which checks below it ran and what it inspected.
   - Checks, always including:
     1. Requirement coverage: map each requirement to a diff line and flag anything missing or partial.
     2. Scope creep: any changed line the requirements did not ask for.
     3. Test validity: would each new test fail if the change were reverted? Look for tautologies, mock echoes, assertions on incidental defaults, and existing tests that got weaker. It reasons about this since it cannot edit, and it runs the changed test files.
     4. Blast radius: grep every caller of each changed export and check the behavior of callers that were not edited.
     5. CLAUDE.md rules: comment style, em dashes, hardcoded pixel widths, secrets, stray files, and the left join with coalesce pattern for DB relationships.
   - Add checks by change type. Client UI: live-region mounting, double announcements, effect dependencies and cleanup, stale closures, narrow-width layout. Server: dynamically built SQL, auth middleware coverage, error paths including `invalid_grant`.
   - Spawn summary: in the same turn, as the last chat text right above each `reviewer` task call (pass 1 and pass 2), print a short plain language summary so the permission prompt has context. Cover: which PR and which pass ("PR 5, review pass 1 of 2"), the diff under review (branch, commit count, files and line stat), the requirements it checks against, the checks it will run including any change type extras, what it cannot do (no edits, read-only git), and for pass 2 the pass-1 findings it must verify. Words only, no code. Keep it to a few lines.
6. Fix. If any finding is blocking, send those findings to the implementer for one fix pass, then run review pass 2. The pass-2 reviewer gets the pass-1 findings and the fix diff, must verify each finding is fixed, then hunts the whole diff again with the same brief.
7. Limit. Two review passes in total. If blocking findings remain after pass 2, stop and report both sides. If the same finding comes back twice, also stop and report, then draft a rewritten brief for a fresh implementer agent and wait for my go before spawning it. Never start a third pass on your own.
8. Hand off. After each commit, first show me the code the implementer applied, before any report. Run `git diff` on the modified source files and print it as chat text (tool output is collapsed in my UI, so a path or a summary is not enough), plus the full contents of any new untracked source files, since `git diff` omits them. For test files, list each new or changed test by name with one line on what it protects, and print the full test code only if I ask. Then report the files changed, the diff stat, the verification commands run with results, a proposed commit message in the CLAUDE.md format, and the exact git commands for me to run, and say if a command is due at that point (for example a local migration before committing). After a PR's review, report each review pass with its findings and how each was resolved, anything unresolved, a draft PR title and body, and the push commands. If the branch noted in step 1 is the default branch, open the first hand-off with a bold reminder to create a new branch before committing or pushing, start the git commands with `git switch -c <name>`, and offer two labeled branch names with a lean. Do not stage, commit, or push.
   - Handoff file: confirm the TL;DR, repo state and what-is-done table in the plan's handoff file (`<plan name>-handoff.md` next to the plan) match `git log` and the review result. Fix it yourself if the implementer missed something, and record each review pass and how its findings were resolved. Mark resolved open items as resolved, do not delete them.
   - Browser checklist: in every hand-off, directly above the proposed commit message (after each commit) and directly above the draft PR title and body (after a PR's review), print a short checklist of what I can and should check by hand in the browser. Build it from the change, not from the app: first list for yourself every behavior this commit adds that a person can reach in the UI (the success path, each distinct error or edge state the UI can show, whether the state is still there after leaving and coming back, the effect on every other page that reads the same data, empty and zero states, unchanged-input cases such as saving without changes), then write at least one item for each. Every item must exercise something this commit added. Do not list behavior from earlier commits, and do not spend an item on navigating to the starting page: put that in one "Start at <URL>" line above the numbered items. Skip anything the tests already prove and anything the UI cannot reach (say so in one line, for example "unknown channel ids are dropped, covered by route tests only"). Each item is one line: where to go, what to do, what I should see. Give 3 to 8 items per commit, ordered by importance, and merge items only when one action shows several results. After the new behavior, add at most 2 generic checks scoped to the new flow, such as no network requests in the DevTools Network tab for a feature that must stay offline, and a narrow width (mobile) check for any visual or layout change. Before printing, check each behavior on your own list against the items and fix any gap. After a PR's review, the checklist walks the whole PR's user flow end to end once, up to 10 items, and still skips what each commit's own checklist already covered one by one unless the flow needs it. If the change has nothing browser visible (for example only store logic or tests), write "No browser checks needed" and one line why. I run the checks while I read the commit message, so do not wait for me to confirm them before moving on, and do not stop after printing the checklist. Exception: when the change is important enough that you would have verified it in a browser yourself (it changes how a real, non demo component behaves, touches auth, deletes or rewrites data, changes a migration, or the tests could not exercise it), run the browser check yourself first and report what you saw, or tell me plainly that I must check it before I commit and wait.
